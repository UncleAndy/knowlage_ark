# M0a, находка 1: полностью статический musl не собирается (и не кэширован)

Дата: 2026-11-17. nixpkgs rev: `f68407657ad294471eb4b2e65d193df26edf729f` (nixos-26.05).
Компонент: `pkgsMusl.pkgsStatic.*` — то есть статическая сборка поверх musl.

## Что измерено

```
$ nix path-info --store https://cache.nixos.org /nix/store/ycm2lddhfpw1ha034fjsaq5wdyvq30j3-stdenv-linux
{ "/nix/store/ycm2lddhfpw1ha034fjsaq5wdyvq30j3-stdenv-linux": null }
```

Путь возвращается как `null`: в бинарном кэше его нет, значит этот stdenv нужно собирать
локально. Попытка сборки (76 с) падает на самой musl, а не на нашем коде:

```
$ nix build -L --no-link --print-out-paths .#probe-x86_64-busybox
musl-static-x86_64-unknown-linux-musl> collect2: fatal error: cannot find 'ld'
musl-static-x86_64-unknown-linux-musl> make: *** [Makefile:162: lib/libc.so] Error 1
error: Cannot build '/nix/store/j69x2ba2jgli5bbgfmhjl9vq6g69004s-musl-static-x86_64-unknown-linux-musl-1.2.5.drv'.
       Reason: builder failed with exit code 2.
```

Дальше отказ идёт по цепочке зависимостей: `musl-static` → `gcc-wrapper` → `stdenv-linux` →
`busybox-static-musl`, и Nix рапортует `Reason: 1 dependency failed` на каждом уровне.

Для сравнения, в тех же условиях:

- `pkgsStatic.busybox` (статическая сборка на glibc) — собралась пересборкой за 25 с (была в кэше);
- `pkgsCross.aarch64-multiplatform-musl.pkgsStatic.busybox` — собралась пересборкой за 25 с (кросс-набор, статическая линковка через обычный stdenv цели), тоже была в кэше;
- локальный стор при этом не повреждён: прежние артефакты валидны, в реестре 78 016 путей.

## Находка 2: `--rebuild` — это не «заставить собрать»

Первый прогон pass1 падал почти на каждой строке с текстом:

```
error: some outputs of '/nix/store/ndxga71qcgvn17kld49b7np669654hj7-linux-aarch64-unknown-linux-gnu-6.18.63.drv'
       are not valid, so checking is not possible
Hint: --rebuild and --check error if the derivation was not previously built and cannot be substituted.
```

Смысл: `--rebuild` означает «пересобери, хотя артефакт уже есть», и он отказывает, если артефакта
нет и подставить его неоткуда. Наше ядро с собственным конфигом в кэше отсутствует по определению
— значит `--rebuild` для него бессмысленен, а обычная сборка как раз и есть сборка из исходников.

Исправлено в раннере: сначала всегда обычная сборка (её время и есть настоящее, если артефакт
не подставился), и только затем, для критичных компонентов, принудительная пересборка — если
выяснилось, что артефакт был взят из кэша или уже лежал в сторе. Провенанс получил четвёртое
значение `present` (артефакт уже был, ничего не происходило): иначе нулевые секунды выглядели бы
как невероятно быстрая сборка.

## Что это значит

Ломается ровно одна комбинация: **нативная полностью статическая сборка на musl** (её
bootstrap-цепочка собирает musl статически, и та падает на линковке). Это не про наш код и
не про порчу стора: сочетание просто не собирается Hydra (отсюда и отсутствие в кэше), и
не собирается здесь.

## Точное место отказа (уточнено по логу сборки)

```
$ nix log /nix/store/j69x2ba2jgli5bbgfmhjl9vq6g69004s-musl-static-x86_64-unknown-linux-musl-1.2.5.drv | ...
x86_64-unknown-linux-musl-ar rc lib/libc.a obj/src/... ; x86_64-unknown-linux-musl-... obj/ldso/dynlink.lo
collect2: fatal error: cannot find 'ld'
compilation terminated.
make: *** [Makefile:162: lib/libc.so] Error 1
```

То есть падает линковка `lib/libc.so` — компоновщик `ld` не найден в окружении сборки мусли. В наборе
собираемых производных присутствует `x86_64-unknown-linux-musl-binutils-wrapper-2.46` и
`x86_64-unknown-linux-musl-gcc-wrapper-15.3.0`, но до самой линковки дело не доходит. Комбинация
`pkgsMusl.pkgsStatic` не собирается Hydra — отсюда и отсутствие в кэше, и то, что дефект никем
не пойман: это непроверенная в CI комбинация, а не сбой нашего кода.

## Открытый вопрос (важно не сделать вывод раньше факта)

Отказ выглядит как `cannot find 'ld'` — подозрительно похоже на особенность окружения
(сборка идёт пользователем, который не входит в `trusted-users`, при `sandbox = true`, в
конфиге `max-jobs = 2`, `cores = 3`), а не на дефект nixpkgs. Тот же заказ от доверенного
пользователя (root) может собраться. Проверить это — отдельный шаг; до его результата
формулировка «musl-static невозможен» неверна, верна только «не собирается в этом окружении».

## Варианты для проекта

1. **Динамический musl** (`pkgsMusl.*` без `pkgsStatic`) для полезной нагрузки ISO. Rootfs наш,
   рядом лежат `libc.so` и прочее; в кэше есть, собирается быстро. Для «Ковчега» это естественный
   основной путь: статика нужна не самой читалке, а простоте доставки.
2. **Статика на glibc** (`pkgsStatic`) — проверено, работает; бинарники крупнее (busybox около
   2–3 МБ), но на флешке это ничто. Подходит для пути ARKBOOT, где хочется один файл без библиотек.
3. **Свой статический musl** (musl-cross-make или Buildroot внутри флейка) — самый чистый вариант
   по духу варианта B, но это отдельный проект инструментария; браться за него стоит только если
   пункт 1 почему-то не подойдёт.

Решение по этим вариантам — за владельцем проекта; оно меняет состав полезной нагрузки, а не
концепцию.
